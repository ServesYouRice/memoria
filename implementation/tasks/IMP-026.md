# IMP-026 — Bounded version history and restore

<objective>
Version storage follows selected retention and restore is atomic, set-based, and
safe during collaboration.
</objective>

<steps>
1. Enforce count/age/byte retention from DEC-008 and reject snapshots outside
   the supported launch envelope.
2. Replace row-by-row restore with bounded staged/set-based operations inside
   one transaction and explicit statement/transaction timeouts.
3. Establish a canvas restore revision/maintenance lock so concurrent writes
   cannot create a mixed state.
4. Commit one new revision and publish a mandatory client reload/delta event.
5. Test large snapshot duration, rollback on failure, concurrent editor writes,
   relations, and post-restore convergence.
</steps>

<acceptance>
- Restore is all-or-nothing and meets the declared duration budget.
- Connected clients cannot continue from stale pre-restore state.
</acceptance>

<verification>
Large real-DB integration test; two-client test; type/lint.
</verification>
