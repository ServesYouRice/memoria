# IMP-132 - Deleted canvases go to Trash for 30 days (server side)

<objective>
Deleting a canvas no longer destroys it at once. The canvas and
everything on it is hidden everywhere, can be restored by its owner for
30 days, and is removed for good after that. This card does the server
and database part; IMP-133 does the screens.
</objective>

<context>
Found in the UI audit of 2026-11-14. Deleting one note is safe: it gets
`deletedAt`, shows in Trash and is swept after
`LAUNCH_LIMITS.trashRetentionDays` (30). Deleting a whole canvas is a
hard delete: `DELETE /api/v1/canvases/[canvasId]` runs
`releaseCanvasUploads`, `tx.canvas.delete` and
`enqueueThumbnailDeletion`, and the dialog says "This action cannot be
undone". The bigger loss has the smaller safety net.
Rule used (WCAG 3.3.4): deletions should be reversible.
Why this card is risky: the `Canvas` model has no `deletedAt` today, and
canvases are read in about 50 files (API routes, agents, extension
routes, sharing, embeds, the sync server, search, AI). A trashed canvas
that still opens through any one of those paths is a privacy bug.
</context>

<files>
`prisma/schema.prisma` (`model Canvas`), `prisma/migrations/` (newest
folder shows the naming pattern),
`src/app/api/v1/canvases/[canvasId]/route.ts` (the `DELETE` handler),
`src/app/api/v1/canvases/route.ts` (list and create),
`src/lib/api/auth.ts` (`getCanvasAccess`, `requireCanvasAccess`,
`requireCanvasOwnership`), `src/app/api/v1/trash/route.ts`,

`src/lib/policy/launch-limits.ts`,
`src/app/api/v1/share/[token]/`, `src/app/embed/[token]/`,
`src/lib/collaboration/` (sync access), `src/lib/agents/`,

</files>

<executor_constraints>
- This card changes who can read what. If you are a small model, write
  out the list from step 4 and ask an advisor model to review it before
  you edit any of those files.
- Schema changes need a migration file. Test against PostgreSQL
  (`pnpm gate integration`), not only with mocks.
- Never weaken an existing permission check or Zod schema.
- A trashed canvas must behave exactly like a canvas that does not exist
  for everyone except its owner's Trash and restore calls: same status
  codes and same error text as "not found", so nothing reveals that it
  is in Trash.
- Do not build "delete forever now" in this card.
- The final removal must be safe to run twice (AGENTS.md job rule).
</executor_constraints>

<steps>
1. Schema. In `model Canvas` add `deletedAt DateTime?` and
   `deletedById String?`, and `@@index([userId, deletedAt])`. Create a
   migration folder under `prisma/migrations/` named like the newest one
   (`YYYYMMDDHHMMSS_canvas_trash`) with the SQL to add both columns and
   the index. Regenerate the Prisma client.
2. Move the three hard-delete calls out of the `DELETE` handler into one
   function `purgeCanvas(tx, canvasId)` in `src/lib/canvas/` and keep
   their order and comments.
3. `DELETE /api/v1/canvases/[canvasId]` (owner only, unchanged check):
   instead of purging, set `deletedAt = now()` and `deletedById`. Keep
   `invalidateCanvasCache` and the `CANVAS_DELETED` activity. Respond
   `200 { message: "Canvas moved to Trash", trashed: true }`.
4. Hide trashed canvases everywhere. Run
   `grep -rnE "\.canvas\.(findMany|findFirst|findUnique|findUniqueOrThrow|findFirstOrThrow|count|update|updateMany)\(" src --include=*.ts --include=*.tsx`
   and
   `grep -rnE "canvas: \{" src --include=*.ts`
   (item queries that filter through the canvas relation). Ignore
   `src/generated/`. For every match decide and note one of:
   - reads or changes a live canvas -> add `deletedAt: null` to its
     `where` (for `findUnique`, add it next to the id);
   - is Trash, restore or the sweep -> must see trashed rows, leave it.
   Start with the central helpers: `getCanvasAccess` returns `"NONE"`
   and `requireCanvasOwnership` throws its normal not-found error when
   `deletedAt` is set. Then cover, at least: the canvases list; canvas
   GET/PATCH; duplicate; public share by token; embed by token; sync
   server access for a canvas document; item list, search and "something
   old"; reminders; agents and extension routes; AI routes; export.
5. Limits. A trashed canvas does not count toward
   `LAUNCH_LIMITS.canvasesPerUser`. Its uploads stay stored and stay
   counted until the final removal.
6. Trash API (`src/app/api/v1/trash/route.ts`): `GET` also returns
   `canvases: [{ id, name, deletedAt, itemCount }]` for the caller's own
   trashed canvases, newest first. Keep the existing `items` field
   unchanged. Do not list items whose canvas is itself trashed.
7. Restore: add `POST /api/v1/canvases/[canvasId]/restore` (owner only,
   Zod-checked params). It clears `deletedAt` and `deletedById`, checks
   the canvases-per-user limit first, invalidates the cache, and returns
   the canvas. A canvas that is not in Trash gives the normal not-found
   error.
8. Sweep. In `createTrashRetentionHandler` also take canvases whose
   `deletedAt` is older than the same cut-off, in batches, and call
   `purgeCanvas` for each inside a transaction. A second run must find
   nothing to do.
9. Tests (PostgreSQL, `tests/integration/canvas-trash.test.ts`):
   after `DELETE`, the canvas is missing from the list; GET and PATCH on
   it answer like "not found"; its public share link and an embed answer
   like "not found"; item search does not return its items; a shared
   collaborator gets "not found"; `GET /trash` lists it for the owner
   only; restore brings back the canvas, its items and its share link;
   the sweep removes it after the cut-off and releases upload quota
   exactly once; running the sweep twice is harmless.
   Add API tests for the new route so the route-coverage check in
   `pnpm gate` passes.
10. Update `tests/integration/canvas-delete-upload-quota.test.ts` and
    other tests that expect an immediate hard delete: the quota is now
    released by the sweep, not by `DELETE`.
</steps>

<acceptance>
- `DELETE` on a canvas keeps its row with `deletedAt` set; nothing is
  purged at that moment.
- Every case in step 9 passes against PostgreSQL.
- The commit message lists each file from step 4 and whether it was
  filtered or left alone on purpose.
- Restoring returns the canvas exactly as it was (items, shares, public
  link, versions, uploads).
- After 30 days the sweep removes the canvas, its uploads' quota and its
  thumbnail, once.
</acceptance>
