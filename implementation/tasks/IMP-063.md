# IMP-063 - Cover API-key management routes

<objective>
Creating, listing, and revoking API keys is covered through the real route
handlers, with one-time plaintext disclosure, hash-only persistence, response
redaction, expiry validation, and ownership enforcement proven independently.
</objective>

<files>
`src/app/api/v1/api-keys/route.ts`,
`src/app/api/v1/api-keys/[keyId]/route.ts`, and a new
`tests/api/api-keys.test.ts`.
</files>

<context>
No unit, API, integration, or E2E test imports either API-key management route.
IMP-056 covers key generation, masking, and
`authenticateApiKey`; it does not exercise the session-authenticated management
surface.

The collection route returns plaintext only after creation and stores an Argon2
hash in the `key` column. List responses intentionally expose preview fields but
must never expose the stored hash or reconstruct a usable key. The item route
soft-revokes a key and must not mutate another user's row.

This is a test-only card. If a route leaks a hash/plaintext key, accepts an
expired creation, or updates another user's key, stop immediately. Do not patch
the route under this card; add one `DEC-` row with the exact request, response,
and unexpected Prisma call.
</context>

<executor_constraints>
- Import the real GET, POST, and DELETE exports. Mock `requireAuth`, Prisma, and
  `generateApiKey`; do not mock the route module or reimplement its mapping.
- Use deterministic dates with fake time for expiry assertions.
- Never perform real Argon2 work in this API suite; IMP-056 owns helper-level
  cryptographic behavior.
- Assert absence of forbidden reads/writes, not only response status.
- Do not change production code or broaden API behavior under this card.
</executor_constraints>

<steps>
1. Cover GET with a signed-in user. Assert the Prisma query is scoped to that
   user's ID and ordered as shipped. Parse the JSON and prove every entry omits
   `key` and `plaintextKey` while retaining only the documented metadata and
   preview fields.
2. Cover POST denial and validation: missing auth performs no generation or
   write; an empty/oversized name, malformed date, and past expiry each return
   the route's validation status before `generateApiKey` or `apiKey.create`.
3. Cover POST success with a fixed generated plaintext/hash pair. Assert the
   database receives the hash, owner ID, expiry, prefix, and suffix, never the
   plaintext. Assert the 201 response returns the plaintext once and does not
   expose the stored hash.
4. Cover DELETE with four separate cases: missing row, another user's row,
   owned active key, and owned already-revoked key. A non-owner must produce no
   update; an active owned key receives `revokedAt`; an already-revoked key
   returns success without a second update.
5. Keep response-shape assertions explicit. Do not snapshot the whole Prisma
   row, because that would make a future credential-field leak easy to bless.
</steps>

<acceptance>
- Only successful creation returns plaintext, and no response exposes the
  stored hash.
- Invalid or non-future expiries cause no key generation and no write.
- Listing is owner-scoped and cannot return another user's rows by construction.
- Non-owners cannot revoke a key, proven by zero update calls.
- Re-revocation is idempotent.
- No production file changed.
</acceptance>

</verification>
