# IMP-100 - Lighter install and set-up checks

<objective>
Running Memoria on a small server is simple: a documented small set-up
with few parts, and a check that says plainly what is wrong when something
is not connected.
</objective>

<context>
Approved by the owner on 2026-11-11: well-liked self-hosted tools start
two or three parts. Memoria's `docker-compose.yml` starts eleven
long-running services by default (app, gateway, scheduler, outbox-worker,
sync, backup, backup-monitor, postgres, redis, minio, edge) plus a one-off
migration; second replicas and monitoring are optional profiles.
`pnpm setup:selfhost` builds and starts the full stack. A separate sync
server is where other projects' support forums fill with "not saving"
reports, usually a proxy that does not pass WebSockets.
</context>

<files>
`docker-compose.yml`, `Caddyfile`, `scripts/`, `README.md`,
`docs/operations/resource-budgets.md`, `docs/operations/runtime-support.md`,
`src/app/api/ready/route.ts`, `src/app/api/health/route.ts`.
</files>

<executor_constraints>
Keep the supported topology explicit: the small set-up is one replica of
each process the product needs and says what it leaves out (for example
bundled object storage, backups, the extra proxy layer) and what the owner
gives up by leaving it out. Do not weaken the full set-up.
</executor_constraints>

<acceptance>
- A documented small set-up starts with one command and runs only the
  parts the product needs, with uploads on local disk.
- Its memory use at rest is measured and written into the resource budgets
  document.
- A set-up check (a command and the first-run page) tests the database,
  Redis, storage, and a live collaboration connection through the proxy,
  and names the fix for each failure in plain words.
- The README shows both set-ups and when to pick each.
</acceptance>

<verification>
`pnpm gate fast`; `pnpm gate container` and `pnpm smoke` on the dev
machine for both set-ups; the set-up check run once with the sync server
stopped.
</verification>
