# IMP-062 - Make nominal API suites exercise their routes

<objective>
The canvas-item API suite invokes production route handlers, and obsolete
template behavior tests are replaced by assertions against the shipped launch
gate, so deleting or bypassing either route makes its test fail.
</objective>

<files>
`tests/api/canvas-items.test.ts`, `tests/api/templates.test.ts`,
`tests/api/template-gating.test.ts`,
`src/app/api/v1/canvas-items/route.ts`,
`src/app/api/v1/canvas-items/[itemId]/route.ts`, and
`src/app/api/v1/templates/route.ts`.
</files>

<context>
Following every import and call in the two nominal API suites shows that neither
currently exercises its named route.

`tests/api/canvas-items.test.ts` never imports a route. It calls mocked Prisma
and mocked authorization functions directly, then asserts those calls. Its
optimistic-locking test therefore cannot fail when the production PATCH handler
loses its version predicate.

`tests/api/templates.test.ts` does the same for template behavior that is not
currently shipped. The real template route exports one disabled handler for GET
and POST. `tests/api/template-gating.test.ts` invokes the real GET handler, but
does not cover the template POST method.

This is a test-truthfulness card. The source routes are subjects to inspect, not
files to edit. If a real handler violates an invariant below, do not rewrite the
test around the defect and do not fix production code under this card. Stop and
record one `DEC-` row naming the route, request, expected invariant, and observed
response/write.
</context>

<executor_constraints>
- Import and call the real exported route method in every behavioral test.
- Mock external dependencies such as Prisma, auth, cache invalidation, activity
  logging, and committed events; never mock the route module or duplicate route
  logic inside the test.
- Keep `tests/api/items.test.ts`; its schema tests exercise real validation code
  and are outside this card.
- Do not raise timeouts, add sleeps, weaken status assertions, or change source
  behavior to obtain green tests.
- Preserve unrelated tests and user changes.
</executor_constraints>

<steps>
1. Rewrite the canvas-item create cases around the real POST from
   `src/app/api/v1/canvas-items/route.ts`. Prove separately that unauthenticated,
   invalid-body, and denied-EDIT requests perform no transaction/write. For a
   valid request, assert 201 and the parsed content, actor IDs, version, and
   canvas ID passed to the transaction's create call.
2. Rewrite optimistic update cases around the real PATCH from
   `src/app/api/v1/canvas-items/[itemId]/route.ts`. Prove a missing/invalid
   version is rejected before a transaction, denied EDIT access performs no
   write, a zero-row versioned update returns 409, and a successful update uses
   `{ id, version, deletedAt: null }` and increments the version.
3. Remove assertions that only prove TypeScript accepts a locally constructed
   Prisma object or that a mock returns its configured value. Retain an
   invariant only when it is observable through the real handler.
4. Move any still-useful template gate assertion into
   `tests/api/template-gating.test.ts`, table-driven over both GET and POST.
   Assert the same 404 Problem Details response and no auth/database read for
   each method, then delete `tests/api/templates.test.ts` because the enabled
   template implementation it describes does not exist.
5. Run each focused suite from a fresh process. If a route import or assertion
   fails because of a product defect rather than test setup, follow the stop
   condition in `<context>`.
</steps>

<acceptance>
- Every remaining test named as canvas-item or template API coverage imports a
  production route handler.
- Removing the create handler's auth/access check or the update handler's
  version predicate makes the relevant test fail.
- GET and POST on the shipped template route are both proven disabled before
  auth and database work.
- `tests/api/templates.test.ts` no longer asserts unshipped enabled-template
  behavior.
- No production file changed.
</acceptance>
