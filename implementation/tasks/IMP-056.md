# IMP-056 - Cover the API-key authentication boundary

<objective>
API-key authentication rejects revoked, expired, malformed, and legacy-plaintext
keys under test, and key generation and masking are proven not to leak.
</objective>

<files>
`src/lib/api/api-key-auth.ts`, `src/lib/api/api-key.ts`, and new tests under
`tests/unit/`.
</files>

<context>
Neither module is referenced by any existing test. `authenticateApiKey` is a
security boundary that authorises every request carrying an `x-api-key` header,
and it currently has no regression coverage at all.

This is the highest-value uncovered surface per hour of work: both modules are
small, pure enough to test with a mocked Prisma client, and need no database,
network, or new fixtures. Follow the mocked-Prisma pattern already established in
`tests/unit/auth-ordering-security.test.ts` and `tests/api/canvas-items.test.ts`.

`generateApiKey` derives its key by base64-encoding 32 random bytes, stripping
non-alphanumeric characters, then slicing to 32. The strip can in principle leave
fewer than 32 characters, which would produce a short key. Prove or disprove this
with a bounded loop rather than reasoning about it.
</context>

<steps>
1. Cover `authenticateApiKey` against a mocked Prisma client: a revoked key
   (`revokedAt` set) is rejected; an expired key (`expiresAt` in the past) is
   rejected; a row whose stored key does not start with `$argon2` is skipped and
   never compared; a key whose prefix or suffix does not match never reaches
   `verifyApiKey`; a missing header returns `null` without a database query.
2. Assert the format pre-check short-circuits before the lookup, so a malformed
   or short header costs no query.
3. Cover the pure helpers in `src/lib/api/api-key.ts`: boundary cases for
   `isValidApiKeyFormat`, and `maskApiKey` never revealing the middle of a key,
   including the short-key branch.
4. Run `generateApiKey` in a loop and assert every result has exactly 32
   characters after the `mk_` prefix and satisfies `isValidApiKeyFormat`. If the
   loop finds a short key, that is a production defect: report it and add a
   `DEC-` row rather than loosening the assertion.
</steps>

<acceptance>
- Revoked and expired keys are proven rejected, not merely absent from results.
- No test performs a real Argon2 hash in a loop; hashing is mocked or the loop is
  bounded so the file stays fast.
- A generated key that is shorter than 32 characters fails the suite.
</acceptance>

<verification>
`pnpm test:file` on the new files; `pnpm test -- --run`; `pnpm lint`;
`pnpm type-check`.
</verification>
