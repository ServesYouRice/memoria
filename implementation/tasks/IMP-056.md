# IMP-056 - Cover and harden the API-key credential boundary

<objective>
API-key authentication queries only active candidates and verifies only Argon2
hashes, while generated keys are always fixed-length, uniformly sampled from
their declared alphabet, and safe to display only in masked form.
</objective>

<files>
`src/lib/api/api-key-auth.ts`, `src/lib/api/api-key.ts`, a new
`tests/unit/api-key-auth.test.ts`, and a new
`tests/unit/api-key-utils.test.ts`.
</files>

<context>
Neither module is referenced by any existing test. `authenticateApiKey` is a
security boundary that authorises every request carrying an `x-api-key` header,
and it currently has no regression coverage at all.

This is the highest-value uncovered surface per hour of work: both modules are
small, pure enough to test with a mocked Prisma client, and need no database,
network, or new fixtures. Follow the mocked-Prisma pattern in
`tests/unit/auth-ordering-security.test.ts`, but import and call the real subject;
`tests/api/canvas-items.test.ts` is tracked by IMP-062 precisely because it does
not do that.

`generateApiKey` derives its key by base64-encoding 32 random bytes, stripping
non-alphanumeric characters, then slicing to 32. This can produce a short key:
32 bytes of `0xff` encode almost entirely as `/`, and the current transform
leaves one character. This is a known implementation defect, not a probabilistic
test hypothesis; the card owns its bounded fix and regression test.
</context>

<executor_constraints>
- Import and call the real helpers. Mock Prisma, Argon2, the rate-limiter
  factory, and cryptographic randomness only at their external module
  boundaries; do not duplicate the subject's decisions inside a fake helper.
- A mocked Prisma client does not apply `where` clauses. Prove revoked/expiry
  enforcement by asserting the exact candidate query and returning no rows; do
  not feed a revoked row back from the mock and expect application code to
  re-evaluate database predicates.
- Do not perform real Argon2 work in a generation loop. Use deterministic
  randomness and a mocked hash for generator cases.
- Production changes are limited to replacing the known variable-length random
  transform in `generateApiKey`. If an authentication test finds a different
  product defect, stop and add one `DEC-` row rather than broadening this card.
</executor_constraints>

<steps>
1. Cover the cheap rejection path: a missing header and malformed/short values
   return `null` without a database query or hash verification.
2. For a well-formed key, assert `findMany` receives `revokedAt: null`, the
   future-or-null expiry predicate, and the derived prefix and suffix. Returning
   no candidates must return `null` without calling `verifyApiKey`; this is the
   mocked query contract for revoked, expired, and prefix/suffix-mismatched
   rows.
3. Return candidate rows deliberately: legacy plaintext storage is skipped;
   an Argon2 candidate whose verification returns false is rejected; and a
   verified candidate returns only the documented user/key metadata. Assert the
   successful path attempts the best-effort `lastUsedAt` update and that an
   update rejection does not turn valid authentication into an unhandled
   rejection.
4. Cover `isValidApiKeyFormat`, `verifyApiKey`'s invalid-hash failure, and
   `maskApiKey` boundary cases. Explicitly prove the middle of a normal key is
   absent from the masked value and retain the documented short-key branch.
5. Add a deterministic regression with a first random batch containing only
   rejected bytes (for example `0xff`) followed by an accepted batch. Replace
   the base64-strip-and-slice transform with rejection sampling over the
   62-character alphanumeric alphabet: ignore byte values at or above 248,
   map accepted bytes by modulo 62, and request additional secure random bytes
   until exactly 32 characters have been produced. Hash only the completed key.
6. Assert the generated value has the `mk_` prefix, exactly 32 following
   characters, passes `isValidApiKeyFormat`, and contains only the declared
   alphabet. Prove the rejected first batch triggers another randomness request
   instead of returning a short key.
</steps>

<acceptance>
- The candidate query excludes revoked and expired rows and scopes by both key
  preview fields; malformed input does no database work.
- Only a successfully verified Argon2 candidate authenticates, and legacy
  plaintext rows are never compared or upgraded silently.
- Every generated key has exactly 32 alphanumeric characters after `mk_`, even
  when the first random batch contains no usable bytes.
- Sampling introduces no modulo bias: byte values 248 through 255 are rejected.
- No test performs real Argon2 hashing or relies on a lucky random loop.
</acceptance>
