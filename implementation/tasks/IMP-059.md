# IMP-059 - Cover agent API authorization

<objective>
Every route under `/api/agent/v1` rejects a missing, revoked, expired, or
wrong-user API key before it reads or writes any record.
</objective>

<files>
`src/app/api/agent/v1/actions/route.ts`,
`src/app/api/agent/v1/canvases/route.ts`, `src/app/api/agent/v1/items/route.ts`,
`src/app/api/agent/v1/knowledge/route.ts`, `src/app/api/agent/v1/mcp/route.ts`,
`src/app/api/agent/v1/providers/route.ts`,
`src/app/api/agent/v1/integrations/route.ts`,
`src/app/api/agent/v1/integrations/ingest/route.ts`, and a new table-driven test
under `tests/api/`.
</files>

<context>
Eight routes, none referenced by any existing test. This is the largest
contiguous block of untested authorised surface in the application, and it is
reachable with nothing but an `x-api-key` header.

Scope is deliberately narrow: authorization only. Behavioral coverage of what
each route does with a valid key is worth having later, but proving the guard
holds is worth more per hour and can be written once as a table over all eight
handlers rather than eight separate files.

Depends on IMP-056, which establishes how `authenticateApiKey` is mocked. Reuse
that setup rather than inventing a second one.
</context>

<steps>
1. Write one table-driven test enumerating all eight routes with their exported
   methods, and assert each rejects a request with no `x-api-key` header.
2. Extend the table with a revoked key, an expired key, and a well-formed key
   belonging to a different user, asserting rejection for each.
3. Assert rejection happens before any Prisma read or write for that route's own
   data. Authorization lookups are expected, so assert on the model calls the
   handler makes, not on the Prisma client as a whole.
4. Record which routes, if any, do not currently fail closed. If one does not,
   stop and report it as a security finding against IMP-058's `DEC-` pattern
   rather than fixing it inside a test card.
</steps>

<acceptance>
- All eight routes appear in the table; adding a ninth route to the directory
  without adding a test is visible, ideally by deriving the list from the
  filesystem.
- A rejection is proven by the absence of the handler's own data access, not only
  by the response status.
- Any route that does not fail closed is reported, not patched here.
</acceptance>

<verification>
`pnpm test:file` on the new file; `pnpm test -- --run`; `pnpm lint`;
`pnpm type-check`.
</verification>
