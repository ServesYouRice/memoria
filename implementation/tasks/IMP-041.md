# IMP-041 - Correct authentication and capability handling

<objective>
Login, registration, lockout, rate limiting, and canvas metadata do not leak
account/capability state or let a locked or distributed attacker bypass the
intended controls.
</objective>

<files>
`src/lib/auth.ts`, `src/lib/auth/account-lockout.ts`,
`src/app/api/v1/auth/register/route.ts`, `src/middleware/rate-limit.ts`,
`src/app/api/v1/canvases/[canvasId]/route.ts`, auth and authorization tests.
</files>

<context>
Confirms Opus LOG-03, SEC-01, SEC-02, SEC-07, and SEC-10. SEC-03 is retained at
Medium scope: the metadata route over-returns a live public-link capability, but
IMP-033 already clears tokens on disable and rotates/mints them, invalidating
the audit's long-lived-token scenario. SEC-06 is not a reproduced leak because
all shipped sign-outs perform a document redirect.
</context>

<steps>
1. Reject an active account/client lock before expensive password work and on
   every outcome, including a correct password, while preserving equivalent
   unknown-user timing and typed user-facing errors.
2. Verify the password before emitting any unverified-email state; make login
   copy and resend behavior enumeration-safe.
3. Make registration's existing-email response indistinguishable from accepted
   registration without weakening invite/closed admission or concurrent unique
   constraints.
4. Add an account-level distributed-abuse control plus authenticated-principal
   limits; retain IP limits for anonymous/auth endpoints and avoid a trivial
   account-targeted denial of service.
5. Replace whole-row canvas reads with explicit role-aware selects. Return
   `shareToken` only to the owner path that manages the link.
6. Keep Redis lockout failures fail-closed in production, but expose a distinct
   operational signal and document recovery rather than silently converting the
   control to fail-open.
</steps>

<acceptance>
- Locked credentials never authenticate and do not trigger Argon2 verification.
- Invalid/unverified/existing-account probes do not disclose account existence
  before proving the relevant authority.
- Distributed attempts encounter an atomic account control, and collaborators
  never receive owner-only capability fields.
</acceptance>

<verification>
Focused auth ordering/timing-shape tests; Redis concurrency tests; metadata
field-level authorization tests; `pnpm type-check`; `pnpm lint`.
</verification>
