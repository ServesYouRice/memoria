# IMP-061 - Ratchet explicit API-route coverage from a measured baseline

<objective>
Every API route module, including untouched files, appears in a dedicated
coverage denominator with a measured non-regression threshold, while the
existing broader loaded-file coverage gate remains unchanged or becomes stricter.
</objective>

<files>
`vitest.config.ts`, a new `vitest.routes-coverage.config.ts`, `package.json`,
and `.github/workflows/ci.yml`.
</files>

<context>
`vitest.config.ts` currently enforces `lines: 52, statements: 51, functions: 49,
branches: 43` over modules loaded by the default suite. Its own comment says to
ratchet these upward as behavioral coverage lands.

The current successful coverage report contains only 9 of 73
`src/app/api/**/route.ts` modules because the config has no explicit
`coverage.include`. Untouched production files are absent instead of appearing
at zero, so the reported global percentage is not a whole-source baseline. The
current loaded-file numbers must not be relabeled as whole-source coverage.

Simply adding all production source to that existing denominator could drive
its measured percentage below an already-enforced threshold and would make old
and new numbers incomparable. Keep the current gate and introduce a separate,
explicit API-route lane. That lane can start at its own measured value without
lowering the existing global floor.

The numbers cannot be measured until the gate is reproducibly green and the
cards that add route coverage have landed. `pnpm test:coverage` passed
immediately after the normal suite failed, and the normal suite then passed on
a repeat. A measurement from that order-dependent gate is not a trustworthy
baseline.

Arbitrary 80-90 percent directory targets have no measured baseline or staged
path. This card records the real numbers and fences them instead of picking an
aspirational target.
</context>

<executor_constraints>
- Do not lower or delete any threshold in `vitest.config.ts` and do not replace
  its existing denominator with a materially different one while preserving the
  old label.
- The route lane must reuse the normal test selection, setup, aliases, and
  environments. Only its coverage include/report/output/threshold settings may
  differ.
- Include `src/app/api/**/route.ts` by path, not by a hand-maintained list of
  currently imported routes. Exclude no route merely because another test layer
  covers it.
- Do not pick an aspirational percentage or weaken tests to reach a target.
</executor_constraints>

<steps>
1. Preserve the existing `pnpm test:coverage` lane and its four thresholds.
   Add `vitest.routes-coverage.config.ts` by merging/reusing the base config,
   with an explicit `coverage.include` for every `src/app/api/**/route.ts` and a
   distinct output directory so untouched routes appear at zero without
   overwriting the primary report.
2. Add a non-watch `test:coverage:routes` package script and run it only after
   IMP-055 through IMP-060 and IMP-062 through IMP-066 have landed. Confirm the
   report's route-file set exactly matches the current filesystem inventory;
   record the commit, file count, metrics, and zero-covered route count in the
   config comment and reported verification output.
3. Set the new route lane's statement, branch, function, and line thresholds
   just below that measured route-only baseline. Use the smallest practical
   margin so deleting meaningful route coverage fails, while never changing an
   existing primary threshold downward.
4. Run both coverage lanes in CI. Retain the route report (or at least its JSON
   summary) as a named artifact so a later executor can compare its baseline.
   Do not remove the existing full-suite coverage step.
5. Prove the denominator behavior without committing a production mutation:
   temporarily exclude one route test and confirm the route lane drops/fails,
   then restore it; separately inspect an untouched route in the JSON report and
   confirm it is present with zero counters.
6. Document that integration/E2E execution is not merged into this V8 report;
   those tests remain valid evidence, but they do not justify relabeling a
   zero-covered unit route as covered in this lane.
</steps>

<acceptance>
- Existing primary thresholds are unchanged or higher, and every new route
  threshold is below the measured route-only value rather than aspirational.
- Every current API route module is present in the route report, including
  zero-covered files; adding an untested route becomes visible and cannot
  improve the route baseline.
- The recorded baseline names the commit, route count, four metrics, and
  zero-covered route count.
- A temporary removal of meaningful covered-route evidence fails the route
  coverage lane, and the mutation is restored before handoff.
- CI runs and retains both the primary and explicit route coverage results.
</acceptance>

<verification>
`pnpm test:coverage`; `pnpm test:coverage:routes`; `pnpm test -- --run`;
`pnpm lint`; `pnpm type-check`. Inspect the retained route report and the CI job
definition; do not claim the remote workflow ran unless it actually did.
</verification>
