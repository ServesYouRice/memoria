# IMP-061 - Ratchet coverage from a measured baseline

<objective>
Coverage thresholds sit just below real measured coverage and can only move
upward, so a drop in behavioral coverage fails the build.
</objective>

<files>
`vitest.config.ts`, `.github/workflows/ci.yml`.
</files>

<context>
`vitest.config.ts` currently enforces `lines: 8, statements: 8, functions: 28,
branches: 50`. Its own comment says to ratchet these upward as behavioral
coverage lands, and nothing has enforced that.

The numbers cannot be revisited until the gate is green and the cards that add
coverage have landed, because `pnpm test:coverage` inherits the failing suite and
cannot currently produce a trustworthy measurement at all.

IMP-049's reconciliation already rejected the proposal to set 80-90 percent
directory targets, on the grounds that they had no measured baseline and no
staged path. That rejection stands. This card is about recording the real numbers
and fencing them, not about picking an aspirational target.
</context>

<steps>
1. Run `pnpm test:coverage` on a green suite and record the actual per-directory
   numbers in the card evidence.
2. Raise the global thresholds to just below the measured values, so the build
   fails on regression rather than on ambition.
3. Publish the per-domain numbers somewhere an executor will see them, so the
   next card raising coverage knows its starting point.
4. Do not set a target that the suite does not currently meet, and do not lower
   any existing threshold.
</steps>

<acceptance>
- Every threshold is at or above its current value and below the measured value.
- The recorded baseline names the commit it was measured at.
- A deliberate deletion of one covered test file fails the coverage gate.
</acceptance>

<verification>
`pnpm test:coverage`; `pnpm test -- --run`; `pnpm lint`; `pnpm type-check`.
</verification>
