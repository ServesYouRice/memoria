<open_questions>
If the person you are working with has answered one, follow the answer; otherwise take the default it states.
- section-8911816ae25d00a3b49e7b7a/Q-001 (blocking: the README asks it first): How should live committed-event gap detection work, given that CanvasEvent.sequence is one BIGSERIAL shared by all canvases (migration 20260728210000_canvas_events) and acceptCommittedEvent in src/lib/hooks/use-collaboration.ts treats cursor > lastCursor + 1 as a gap? Option A: add a contiguous per-canvas counter. Allocate it in the same transaction with UPDATE "Canvas" SET "eventSequence" = "eventSequence" + n ... RETURNING, add it to the envelope, and detect gaps on it. This needs a migration and a backfill, serializes event writes per canvas, and changes the committedEventEnvelopeSchema contract. Option B: carry the previous per-canvas cursor in each published envelope. Option C: stop live gap detection and rely on reconnect replay. Option A is the only option whose contiguity rests on documented behaviour: PostgreSQL holds row-level locks until the transaction ends and discards the increments of rolled-back transactions (PostgreSQL docs, Explicit Locking: Row-Level Locks). It is recommended on that basis, but it changes a public API cursor and write concurrency, so the owner must choose. Options B and C are not known to work: B depends on publish order matching commit order, and C silently loses events dropped by pub/sub. The same defect also appears in another section's issue C-3f559b498697 ('Global event sequences are incorrectly treated as contiguous per-canvas cursors'), so the decision and ownership must be coordinated with that section to avoid two competing fixes.
</open_questions>
