<goal>
Stop the reconcile path (applyItemState/fillItemMap via noteDocumentFromContent) from wiping collaborative notes whose stored content exceeds the length limit only because of plainText and rendered text, and make any normalization failure non-destructive for existing fragments.

This matters because it fixes:
- Row-to-document reconciliation replaces long collaborative notes with an empty paragraph (high)
  The two directions of the note conversion apply the 50,000-character limit to different inputs. readNoteFragment, which reads a client's document into a row, passes only `{ formatVersion: 1, document }` to normalizeNoteContent, so only the document JSON is measured. The accepted VersionedNoteContent then gets `plainText` and the rendered HTML `text` added to it, and projection stores that whole object in CanvasItem.content. The reverse path, noteDocumentFromContent, sends the stored object back through normalizeNoteContent. That function measures `JSON.stringify(input)` across all fields. A stored note whose document JSON is under 50,000 but whose total with plainText and HTML is over 50,000 therefore throws on the way back. noteDocumentFromContent catches every error and returns an empty paragraph. fillItemMap sees that the empty document differs from the current fragment and writes it into the note with writeNoteFragment.
