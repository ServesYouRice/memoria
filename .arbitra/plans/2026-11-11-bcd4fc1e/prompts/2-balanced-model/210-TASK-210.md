<goal>
Call assertCanvasItemCapacity under the canvas lock before restoring items in the Trash PATCH route and in the archive revert path (revertArchivedItem / revertChangeSet), and reject atomically when the limit would be exceeded.

This matters because it fixes:
- Trash restore and archive undo bring items back without the per-canvas item cap check (medium)
  assertCanvasItemCapacity counts only live items (`deletedAt: null`), so items in the trash do not count toward LAUNCH_LIMITS.itemsPerCanvas. Two code paths set `deletedAt` back to null and never call assertCanvasItemCapacity. The first is the trash restore PATCH. The second is revertArchivedItem, which runs when an archive change set is undone. The reference list for assertCanvasItemCapacity confirms that neither path calls it. A user can fill a canvas to the cap, delete or archive the items, create new items up to the cap again, and then restore the old ones. Each round adds more live items, so the count has no upper bound.
- Archive undo can restore a canvas beyond its item limit (medium)
  <quotes> await assertCanvasItemCapacity(tx, canvasId, positions.length); </quotes> The capacity policy counts live items, so archiving frees capacity that other creation paths can consume. Undo makes archived items live again without checking that policy. Consequently, refilling a canvas after an archive and then undoing the archive exceeds the enforced item limit.
</goal>
