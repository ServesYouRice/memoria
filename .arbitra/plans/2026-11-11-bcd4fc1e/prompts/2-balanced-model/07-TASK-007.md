<goal>
Ensure version restore and the sync projection re-create path clear archivedAt when they clear deletedAt, harden normal delete paths, and repair existing live rows with a stale archivedAt.

This matters because it fixes:
- Two restore paths leave CanvasItem.archivedAt set, so a later normal delete is kept in Trash forever (medium)
  Migration 20261105220000_weekly_recap adds CanvasItem."archivedAt" as a free nullable column. The schema documents it as being set together with deletedAt when an item is archived, but nothing in the database enforces that. The trash retention sweep skips every row whose archivedAt is non-null. Only two paths clear archivedAt when they un-delete an item: the Trash restore route and the unarchive in services/archive.ts. Two other paths do not: 1. The version-restore SQL sets "deletedAt" = NULL and "deletedById" = NULL but never touches "archivedAt". 2. The sync projection does the same when a known item id is re-created (the comment calls this "an undone deletion"). In both cases an archived item comes back as a live item that still has archivedAt set. The ordinary delete paths (canvas-items DELETE, canvas-items commands, the projection delete, and the restore route's own delete-missing step) set deletedAt and deletedById but also leave archivedAt alone. The row then sits in the trash with a stale archivedAt, and the retention sweep never purges it.
</goal>
